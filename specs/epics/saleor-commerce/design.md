# saleor-commerce — design

## 1. The storefront

Saleor's "Paper" storefront (saleor/storefront `a6e357a`): Next.js 16.4 App
Router, about 60k lines. Routes under `(storefront)/[locale]/[channel]`
(home, categories, collections, products, search with filters, cart,
account, orders, sign-in), a multi-step checkout under `(checkout)`, route
handlers for Saleor's webhook (`/api/revalidate`), Open Graph images
(`/api/og`, `next/og`), auth and listings. Every Saleor read goes through one
data layer (`src/lib/saleor`): typed GraphQL operations generated by codegen,
each a `"use cache"` function tagged by entity (`product:<slug>`,
`category:<slug>`, `navigation:<channel>`, …) with a named `cacheLife`
profile. The webhook plans which tags a delivery invalidates and calls
`revalidateTag(tag, profile)`. Upstream turns on Cache Components (partial
prerendering) and Instant Navigations; it needs a reachable Saleor API to
generate its types, to lint its GraphQL and to build.

## 2. Vercel → Cloudflare

| Vercel | Here |
|---|---|
| Next.js hosting | `@opennextjs/cloudflare` 1.20.11: one Worker (`.open-next/worker.js`) + Static Assets |
| Data Cache | R2 (`NEXT_INC_CACHE_R2_BUCKET`), a bucket per environment from `infra/terraform/cloudflare-r2` |
| Tag revalidation | the sharded Durable Object tag cache (`NEXT_TAG_CACHE_DO_SHARDED`) |
| Stale-while-revalidate | the Durable Object queue (`NEXT_CACHE_DO_QUEUE`) through `WORKER_SELF_REFERENCE` |
| Image Optimization | off — Saleor's thumbnail endpoint sizes images |
| Env vars | the API URL and channel as optional build secrets; the revalidation secrets and app token as Worker secrets |

## 3. The cache

The commerce baseline's shape, unchanged: R2 incremental cache, sharded
Durable Object tag cache, Durable Object queue — `open-next.config.ts`, the
bindings and the `migrations` in `wrangler.template.jsonc`. The brief named a
D1 tag cache as the fallback; the Durable Object one is the reference's
proven choice, needs no database to provision or seed, and is strongly
consistent per tag shard.

## 4. Cache Components off, `"use cache"` kept

On workerd through the adapter a Cache Components page answers 500 and then
hangs (opennextjs-cloudflare#1450; the fix, #1318, is unreleased) — the row
before this one stopped on it. So `cacheComponents` and
`partialPrefetching` are off and `experimental.useCache` keeps every
`"use cache"` read with its profile and tags; routes render per request from
cached reads. The five `instant` / `prefetch` route segment configs are
Cache Components options (the build refuses them without it) and are
removed. The spike measured it under `wrangler dev`: a second visit reads
Saleor not at all, and a tag revalidation re-reads exactly that entry. Next
is 16.3.8: 16.4.x fails every request on the adapter's newest npm release.

## 5. The schema

`apps/web/schema.graphql` is Saleor's published schema
(`saleor/graphql/schema.graphql` at 3.23.44; Paper needs 3.23+). Both codegen
configs and the GraphQL lint read it, so the build, the type check, the lint
and the tests need no store; the checkout's committed types regenerate
byte-identical from it. A newer Saleor is a replaced file.

## 6. Before a store, and after

Saleor has no public demo API the template points at, and a bundled
catalogue would fake 27 deep queries in the Worker. So the template's own
unconfigured state is made explicit: `src/lib/saleor-connection.ts` says
whether the build had an API URL; unconnected, the storefront has no
channels (nothing prerenders or calls Saleor), the middleware redirects every
page to `/`, the checkout layout too, and `/` says "Connect your Saleor
store". The auth client reads the URL when it is made, not at import. The
owner sets `SALEOR_API_URL` (and `SALEOR_CHANNEL`) — optional build secrets,
inlined because the browser's checkout calls the same API — and redeploys.
`NEXT_PUBLIC_STOREFRONT_URL` is each environment's `SITE_URL` or workers.dev
URL. `/api/health` reports the connection for the smoke and the record.

## 7. Tests

Upstream's vitest suite (787 tests) runs unchanged. `tests/web` covers the
port's seams: the store name, the connection, the middleware's redirects,
`/api/health`, the revalidation route's bearer secret and Saleor's signed
webhook. The e2e serves the bootstrapped product twice: as born (the deploy's
own smoke, the unconnected routes), then rebuilt by the stage lane's own
build step with a stand-in Saleor connected (`testing/lib/fake-saleor.mjs`:
graphql-js over the published schema, one default resolver by type and field
name, deterministic and consistent slugs) — catalogue pages, cache reuse, a
change that stays cached until a signed webhook names the product.

## 8. The rename

Slug `saleor-commerce`, Pascal `SaleorCommerce`, store name `Saleor Store` at
the `SITE_NAME` seam (`src/config/brand.ts`); upstream's five other spellings
of the name read it, and the leak gate fails a sixth. The storefront's own
word `Saleor` is not the identity and no rule touches it.

## 9. Alternatives rejected

- **Cache Components on, a patched adapter**: hacking around an open upstream
  bug; the row before this one stopped rather than do it.
- **A D1 tag cache**: a database to provision and populate for what a Durable
  Object does with no root.
- **A bundled demo catalogue**: 27 typed queries faked in the Worker, and a
  checkout and accounts that still need a real store.
- **Saleor's demo store as the default API**: a stranger's catalogue in
  somebody's store, gone when Saleor moves it.
- **Dropping `/api/og` to fit Workers Free**: a template feature removed to
  save 0.6 MiB; Workers Paid is stated instead.
